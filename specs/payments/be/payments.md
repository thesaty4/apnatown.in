# BE: payments

Features: F-CK-006, F-CK-007, F-OR-006, F-VD-017, F-PV-008; gated Account integration F-AC-001, S-CUST-24 | Rules: BR-01, BR-02, BR-03, BR-20 | State machines: ST-payment, ST-refund | Depends on / used by: cart-checkout, orders, delivery, businesses, settings; `offers` consumes paid-promotion events. Cross-module access is through typed contracts/events only.

Frontend counterpart: [FE payments](../fe/payments.md) · [Feature inventory](../../../docs/design-context/01-feature-inventory.md)

## Responsibility

Own payment attempts, verified financial outcomes, pre-order compensation, refund execution and vendor billing projections. Integrate through `PaymentProvider`; provider/capture topology remains gated. Cart/Checkout orchestrates placement; Orders authorizes refund decisions; Offers alone owns promotion placement.

Use [foundation](../../_foundation/backend-shared.md) **flat** errors `{code,message_key,status,details,correlationId}`, CSRF/session guards and allow-listed DTOs. Money is `bigint` paise in storage and safe-integer paise **numbers** in JSON; all intermediates use shared integer math and reject unsafe serialization. No credentials/raw provider payloads in APIs, logs, analytics or events.

## Rules and use-cases

`PaymentAdminReadPort.metrics` implements the scope-first [Admin reporting definitions](../../admin/be/admin.md#reporting-definitions). Use the same immutable financial facts/policy versions as owner earnings; incomplete legacy data is marked unavailable, never a fabricated total or private-ledger export.

Implement its exact repeat-cohort, category-independent top-vendor/completed-count and common-asOf projections. Retain immutable checkout/customer/business/scope references from trusted order context with the existing ledger/allocations; hydrate missing order facts only through Orders' bounded internal ports, never Admin direct-table joins. Compute distinct checkout/customer cohort aggregates inside Payments; expose counts/rate only. Top vendors are selected over the full authorized cohort, not a truncated business-ID page. No-charge recognition uses the settlement evidence below.

1. Compute payable amounts from the checkout quote or configured plan/promotion price. Accept only identifiers/methods, never client prices, commission, payout or refund amounts (BR-01).
2. Keep ST-payment: pending → paid/failed, cash pending → collected, fully returned paid/collected → refunded. Retry creates a new pending attempt in a fenced round; it does not erase the old attempt or prove an unknown capture failed. Browser return is not proof of payment.
3. Keep one authoritative per-shop payment allocation for each order (BR-03). A physical `payment_charges` row may fund one/many allocations without double counting; validate allocation sum against charge funding. Lock both allocation and shared charge before reserving any refund/compensation budget. Q-21 chooses topology, not whether duplicate funding is safe.
4. Verify webhook signatures before parsing business data; deduplicate provider event IDs and validate provider/attempt/amount/currency against the stored request. Never log raw payloads, credentials or full payment details.
5. Refund request/decision is not execution. Only Orders' configured authorized decision, committed with `refund.approved`/`refund.declined` through the ports above, changes the request decision; `refund.escalated` follows source ST-refund. Reserve funds in that UoW so concurrent approvals cannot each spend the same remaining balance. Missing authority/amount policy leaves request pending with policy unavailable. Provider failure leaves approved + processing failed, **never** declined/completed. Only verified provider/cash-return evidence permits completion; no admin “mark refunded”.
6. Emit the refund/payment events through the transactional outbox. Orders/Notifications handle the BR-20 customer/admin/vendor notices; Payments does not send duplicate notices.
7. Cash remains pending until explicit verified handover collection. Delivery calls `recordCashCollection` in the same UoW as code consumption/order handover for platform, self-delivery and pickup. Lock financial version/current payable; a stale job COD snapshot is not charge authority. Exactly one collection key per handover; no duplicate collection on retry.
8. Use the launch billing policy below and current configured plan/promotion prices. Snapshot price/tax/configuration and the period rule before payment; replay preserves them. Retry after changed/expired configuration requires re-review. New authorizations require live `payments_online`; disabling it later does not discard an already verified payment or its entitlement.
9. Featured listing eligibility is a read of the current Premium subscription effective at the requested UTC instant; Payments remains authoritative. Missing subscription data/policy is unavailable, not active. Product/Service selected flags are not payment or placement records, and selecting a listing never initiates a purchase. After expiry, retain owner selections but make effective featuring false; a verified renewal automatically restores effective featuring for still-selected, otherwise-eligible listings without a listing write.
10. Vendor/provider cancellation keeps all already-paid entitlement through `paidThrough`, with no payment-provider call, refund or early de-featuring. Missing legacy expiry is explicitly unverified, not an invented date.
11. Sale/commission posting requires fulfilled and verified-funded orders. Freeze the effective subscription commission rate at checkout, apply it to merchant merchandise value excluding tax after merchant discounts (before platform subsidy), and round half-up once per order. Self-delivery fees, tax, platform fees and platform-arranged delivery are not commission base. Refund reversals use original line/rate shares, not today's rate. Stable source keys prevent duplicates. Earnings is an operational accrual, never proof of payout; Q-75 settlement remains separate.
12. Resolve the vendor/provider and business kind from the authenticated context on every read/write. Foreign IDs cannot expose billing. Admin financial access uses only the existing scoped report ports.
13. Compensation for captured-but-unplaced checkout is a separate technical return obligation, not a customer refund requiring an order/approver. Persist it outside the rolled-back placement UoW; lock/reserve remaining funding and use a stable provider operation key. Approved adapter policy selects void/refund; unknown operation/outcome stays reconciliation_required. Online checkout is unavailable if no executable compensation/reconciliation is configured (Q-01/Q-21/Q-73).
14. Provider success for a closed/superseded/expired round records the actual capture and publishes `payment.late_capture_detected` for compensation; it cannot bind to a newer round or COD order. Ignore stale failure after verified success; never ignore real late funds just to satisfy an enum. Reconcile anomalies against charge facts while preserving the original logical attempt history.
15. Sum completed + in-flight refund/compensation amounts ≤ funded allocation **and** captured shared charge. Reserve/commit before outbound provider call, then apply verified outcome in another transaction; never hold DB locks across provider I/O. Timeout keeps budget reserved until authoritative reconciliation. Partial refunds remain disabled under Q-76 except when its owning approved policy permits them; coupon/tax allocation is now defined by Offers/Orders and never creates extra refund authority.

### Zero-payable order settlement

An exact server-validated zero customer payable is not a provider payment or cash collection. Extend the **internal** allocation method with `no_charge`; never accept it as a client payment method. Preserve ST-payment's `paid` storage value as “settled” for this method only, with `OrderPaymentSummary.settlementKind:'provider'|'cash'|'no_charge'` and `fundingSatisfied:boolean`. UI must label `no_charge` as “No payment due”, never cash collected or a gateway charge. Require current payable, funded, returned and reserved-return amounts all zero, no charge/collection references, and `purpose='order'`.

- `PaymentsOrderPort.settleNoCharge({orderId,paymentAttemptId,quoteId,financialVersion,sourceKey},uow)` is Orders-only. Lock/verify the allocation and pinned quote/current approved revision; require exact zero, current ownership/business eligibility and coupon commitment when applicable. Persist `settlement_key UNIQUE`, `settled_at`, `settlement_financial_version` and the source snapshot with order/coupon/stock/payment links in the **same** UoW. Matching replay returns the same result; mismatches conflict. A rollback leaves no settled order, coupon use or subsidy posting.
- Prepare a zero allocation without creating a `payment_charges` row, provider request or collection. Mixed checkouts send only positive allocations to the selected provider/cash path. Placement waits for all positive online allocations to be verified, or normal cash authorization, plus every zero allocation's valid source; finalize zero settlement atomically with the complete order set. An entirely zero checkout follows this UoW directly, with no synthetic `payment.succeeded` callback. Existing positive-amount charge/compensation rules are unchanged.
- Existing `startOrderPayment/retryOrderPayment` create the zero allocation IDs too; trusted `method` may be omitted only for all-zero inputs, with no-charge derived per allocation from the pinned quote. They do not mark zero allocations settled before Orders' UoW. `closePaymentRound` fences an unsettled zero allocation locally with no external cancellation/compensation.
- `fundingSatisfied` means positive customer obligations verified **or** durable zero-charge settlement, never `status='paid'` alone. Fulfilled no-charge orders can therefore recognize their frozen merchant/platform contribution correctly while customer cash funded remains zero. A platform-funded 1000-paise invoice paid entirely by coupon posts 1000 of campaign funding, zero customer funds and no provider fee/charge; merchant-funded free goods have zero merchant consideration.
- Allowed unpaid-cash adjustments that reduce payable to zero use the same port/current financial version, only with no captured/collected exposure; retain the original quote/amount and adjustment history. This does not authorize a previously gated adjustment. Subsequent handover needs codes/normal fulfilment checks, but never cash confirmation or `recordCashCollection`.
- `PaymentsOrderPort.reverseNoCharge({orderId,sourceKey,financialVersion,orderDecisionId},uow)` is Orders-only for an accepted cancellation/authorized return; validate that decision and derive reversal from original shares, never client amounts. Reverse subsidy/accounting with the owning credit document, without a zero refund/compensation record, fake returned money or restored coupon use/budget. Stable source/reversed-entry constraints prevent replay/over-credit; refund budget stays zero. Return eligibility remains Orders-owned.
- Migration adds the internal method and settlement fields with constraints before enabling zero-payable placement; do not infer settlement for legacy zero rows. Acceptance: test all-zero and mixed 0/positive checkouts, merchant/platform-funded coupons, exact-zero versus unknown totals, zero-after-authorized-adjustment, retry/crash/expired coupon and forged no-charge requests. Only committed zero obligations settle once; no provider/collection/refund operation is emitted for them.

### Launch billing policy

**Decision 2026-11-11: Q-74 plan/promotion timing and cancellation are resolved here.** Keep the configured plan catalogue; paid amounts are explicit Super Admin configuration in Settings, not prototype sample prices or an invented universal market price.

- Paid plans last **one calendar month**, adding a month in IST with day clamped to that month's last day (Jan 31 -> Feb 28/29), preserving local time and storing UTC. Basic/free is non-Premium, uses the configured default commission and needs no payment/expiry row. `premium=true` is an explicit plan entitlement, never inferred from a label/price. No trial, automatic renewal, saved-card mandate, proration or mid-period switch.
- For a new/expired business, the period starts at the first durably verified payment instant. Renewing the same plan or switching plans while active purchases the next full period starting at existing paid expiry; the current interval/rate never changes. Allow at most one paid future period; show it and reject another advance purchase with `SUBSCRIPTION_FUTURE_PERIOD_EXISTS` (409). A queued paid plan starts at its recorded boundary even if the expiry worker runs late.
- Add Payments-owned `business_subscription_versions(business_id uuid PK FK businesses,version int NOT NULL DEFAULT 1)` as the lock/version for the whole current/next chain. Before authorizing a new plan payment, serialize on this row, reject an unresolved plan purchase for that business, validate at most one future term, and persist the pending purchase. Revalidate and insert the non-overlapping period after verified payment under the same lock; increment the aggregate version once. `SubscriptionDTO.version` and all `subscriptionVersion` events/projections refer to this aggregate, not a row version that resets on renewal.
- Persist `billing_purchases.configuration_snapshot jsonb NOT NULL` containing reviewed price, premium, commissionBps, period rules and tax snapshot; copy immutable `{planKey,premium,commissionBps}` into `business_subscriptions.plan_snapshot`. Current Settings edits never change purchased entitlements/rates. Legacy missing snapshots stay unavailable until verified, never inferred from today's catalogue.
- Before payment, show tax-inclusive price, the one-month rule, expected next start and no-auto-renew/no-refund cancellation terms. Pin a configuration/tax quote for 15 minutes. Late success must still be reconciled; if a safely applicable period cannot be granted, return funds through technical compensation rather than silently charging for nothing. Price changes affect new/reviewed purchases only.
- Cancellation is available to both approved vendor and provider owners. Under aggregate lock/version and idempotency key, record `cancellation_requested_at` on every currently purchased unexpired term; retain all periods and paid access through the end of the chain. Replayed same-key requests return the original result before stale-version checks. Later explicit renewal creates a new uncancelled paid term; it is not automatic. Normal cancellation has no refund; duplicate charges or platform failure remain technical compensation, not cancellation exceptions hidden in UI.
- Expiry/renewal reads use half-open intervals and `premium` from the purchase snapshot. Retained owner selections reactivate only during an active Premium interval; a queued non-Premium plan does not restore featuring. An expiry check tests Premium continuity at the boundary; later subscription events cannot regress a newer aggregate revision.
- Purchased promotions last **7 consecutive 24-hour days** from verified purchase (or the end of an existing paid placement on renewal). Offers must approve/preconfigure the target/creative before charging; one current plus at most one future purchase per business/surface, serialized in purchase preparation. Pause, voluntary cancellation or policy suspension does not stop the paid clock or grant a refund. Never extend a period on worker replay. A purchase that never received any placement because of a platform failure must be compensated; transient/unknown outcomes remain visible reconciliation, not success.
- Promotion purchase preparation shares the business billing lock above and rechecks pending/current/future purchases for that surface before creating another intent; Offers preparation joins the caller's UoW. Activation and billing compensation lock the same purchase and persist one terminal disposition: compensation fences all later activation/replay. Never compensate a granted period or grant a compensated purchase.
- Reuse `payment_compensations` for failed billing activation: add nullable `billing_purchase_id`, allow checkout/quote/round references null **only** for billing, and CHECK exactly one complete checkout-round reference or billing purchase reference. `requestBillingCompensation({purchaseId,paymentAttemptId,sourceKey,reasonKey})` is internal; reserve against the same allocation/charge return budget. It cannot refund an already-granted/consumed entitlement or a normal cancellation. Verified completion sets purchase activation failed/compensated and issues the matching credit document; no fictitious order is created.
- Payments owns `billing_documents` and `billing_invoice_counters`, mirroring the pure [Orders InvoiceSnapshot/numbering contract](../../orders/be/orders.md#invoice-and-tax-policy), not a second tax engine. Document sources are one verified purchase or one recognized commission entry, unique by source/supplier/kind; `(business_id,issued_at DESC,id DESC)` serves the owner list. `GET /payments/me/invoices/{documentId}` reauthorizes owner/business kind/purpose and serves an issued snapshot only. Providers can access their plan and own product-order commission documents, never another business's invoices.
- Migration creates aggregate version rows before enabling writes; validate existing periods for overlaps/missing expiry rather than assuming Premium. Old paid price/rate/period snapshots remain immutable. Billing document numbers retain verified legacy evidence; unverified historical rows remain explicitly marked, not invented.
- Acceptance: Given Jan 31 payment, then expiry clamps correctly in leap/non-leap years. Given simultaneous renew/switch/cancel, replayed webhooks or a stale aggregate version, then one paid period/charge outcome is applied and no overlap or paid-time loss occurs. Given an advance renewal then cancellation, then all paid time remains, no refund occurs, and feature expiry happens at the actual final Premium boundary.

## Events and jobs

All messages use the [commerce envelope](../../orders/be/orders.md#event-contracts), transactional outbox/inbox and aggregate-version/source-key deduplication.

| Producer → consumers | Exact event and payload |
|---|---|
| Payments → Products/Services/Search | `business.subscription.eligibility_changed {businessId,subscriptionVersion,endsAt?}` after verified subscription activation or a committed eligibility change; consumers invalidate that business's effective-featured projection/cache tags. Reads still check `at` against the effective interval, so expiration cannot extend featured eligibility. |
| Payments → Products/Services/Search/Notifications | `business.subscription.expired {businessId,subscriptionId,subscriptionVersion,endsAt}` once when the configured end instant passes without a continuous Premium entitlement. Product/Service/Search invalidate effective-featured projections; Notifications sends the scoped expiry notice. |
| Orders → Payments | `refund.requested`, `refund.approved`, `refund.declined`, `refund.escalated`: canonical payloads in Orders. Buffer/retry a decision received before its request; never grant authority based on event arrival order. |
| Orders → Payments | `order.created` links per-shop allocations; `order.status_changed` supplies fulfilment; `order.items_adjusted` refreshes financial projections using adjustment/financial version. No `order.placed` event. |
| Payments → Cart/Checkout | `payment.succeeded` / `payment.failed` `{checkoutAttemptId,paymentRound,quoteId,paymentAttemptIds,amountPaise,exposure,failureCode?}`; success only once all required allocations are verified for that round. `payment.late_capture_detected` adds `paymentAttemptId,chargeId,capturedPaise` for a closed round; never an instruction to place orders. |
| Payments → Orders/ledger | `payment.cash_collected {orderId,paymentAttemptId,collectionKey,amountPaise,financialVersion,collectedAt}`; produced by Payments, not an undefined `cash.collected` input. |

Distinct from Orders' approval/decline decisions; technical failure cannot regress the decision tracker. |
| Payments → Cart/Checkout | `payment.compensation_completed` / `payment.compensation_failed` `{compensationId,checkoutAttemptId,paymentRound,quoteId,paymentAttemptId,amountPaise,status,failureCode?}`. Emit completion only after verified return/void; attempt aggregates all required compensations. No order ID required. |
| Payments → Businesses/Notifications | `business.plan.purchased {purchaseId,paymentAttemptId,businessId,planKey,amountPaise,configurationVersion,period:{startsAt,endsAt}}` after verified purchase and idempotent subscription application. |
| Payments → Offers/Notifications | `business.promotion.purchased {purchaseId,paymentAttemptId,businessId,promotionKey,placementId,amountPaise,configurationVersion,period:{startsAt,endsAt}}`. Offers owns activation/expiry; successful charge with blocked placement remains visibly distinct. |

For each verified finite subscription, schedule a delayed `subscription.expire-due` pg-boss check from the committed outbox event using a stable key based on subscription ID and immutable `endsAt`. At the end instant, re-read the current subscription row/version and entitlement at that exact instant; emit `business.subscription.expired` through the outbox only if Premium was no longer continuous. A renewal effective at the boundary suppresses the expiry event; a later renewal does not erase a real gap. Duplicate jobs/outbox delivery cannot duplicate notices. Cancellation leaves the scheduled check and original `endsAt` unchanged.

The expiry check locks `business_subscription_versions`, not a resetting row version; boundary eligibility changes increment that aggregate once under a durable unique subscription/boundary claim. Emit the current aggregate revision. Retrying a processed boundary cannot decrement a newer entitlement projection.
Extend `earnings.entry_type` with `platform_fee|platform_delivery|platform_coupon_contribution`; each immutable entry stores `tax_paise`, original `tax_snapshot` and optional `reverses_entry_id FK earnings`. Refund entries reverse original components proportionally, never apply current tax/commission. Stable source keys include order/financial version/component; contribution is campaign funding, not platform income/captured customer money. Owner summaries exclude platform-only entries; reporting-v1 sums the defined components, not every ledger row.
`payment.billing_compensation_completed|payment.billing_compensation_failed` carries the billing recovery payload above; only billing recovery/document consumers handle it. Never send a billing-only payload to Checkout's compensation consumer.

Jobs: bounded provider calls, refund/compensation retry, subscription expiry checks and webhook reconciliation. Retry the same provider key; terminal/unknown failure stays observable, not silently dropped or auto-marked paid. Actual settlement producer/commands remain absent until Q-75 is approved.

## Acceptance criteria

1. Given a multi-shop checkout, when Payments confirms every required online allocation, then checkout receives one idempotent success result and each resulting order links its own Payments-owned allocation.
2. Given the provider redirects the browser but no valid signed success event exists, when checkout refreshes, then the attempt remains pending and no order is reported as paid.
3. Given the same webhook is delivered twice, when the second delivery is processed, then payment/order events and ledger entries are not duplicated.
4. Given a webhook signature, amount, currency or attempt reference is invalid, when received, then it is rejected and no payment state changes.
5. Given an authorized cash order, when handover is confirmed, then its payment changes from pending to collected exactly once; order placement alone does not collect it.
6. Given a refund amount exceeds the remaining captured amount, when Orders requests it, then Payments rejects it without calling the provider.
7. Given a vendor requests another business's earnings or starts a purchase for it, when the business ID is altered, then the request is denied without disclosing that business's records.
8. Given an unconfigured plan, promotion, commission or settlement rule, when the vendor opens Earnings or starts a purchase, then no sample value or success-shaped fallback is shown.
9. Given an authorized, configured plan purchase and a verified successful payment, when the event is applied, then the subscription period starts only once and the effective plan is returned from the subscription record.
10. Given capture succeeds but zero orders commit, when compensation/recovery runs twice, then one return obligation per allocation is persisted without an order FK and the customer can observe pending/completed/blocked recovery.
11. Given late capture races a retry/COD fallback, when processed, then old funding is reconciled/compensated and cannot pay or place the replacement round.
12. Given approval arrives before request, duplicate decisions or delayed provider outcomes, when processed, then refund state is monotonic, provider execution occurs once, and only `payment.refund_completed` records returned money.
13. Given shared funding and concurrent refund/compensation requests, when budgets are reserved, then completed + pending returns never exceed allocation or charge funding.
14. Given a configured purchase fails, when its owner reads/retries it, then status is recoverable after reload and retry cannot double-charge, extend a period or bypass new suspension/disabled flags.
15. Given earnings/invoice/settlement policy is missing or Q-33 remains open, when read, then unknown fields/features are explicitly unavailable, not zero totals, seeded invoices, fake empty saved methods or a payout promise.
16. Given a current cash payable differs from an old job snapshot, when handover submits the old financial version, then collection fails without consuming the code; current-version collection uses the revised amount once.
17. Given an erase request lacks approved policy or has unfinished refunds, when processed, then the receipt is blocked and retained financial facts/provider secrets are not erased/exported as a workaround.
18. Given concurrent case decisions, adjustment or another return against shared funding, when `commitDecision` runs, then case decision/outbox/reserved budget commit together or all roll back; a later decision event never reserves twice. Policy-unavailable or projection-pending context cannot approve.
19. Given a business has an active Premium subscription, when Product/Service asks `featuredEligibility` at a UTC instant inside its effective interval, then Payments returns active; before start, after expiry or with unresolved subscription policy, it returns not-active/unavailable and never authorizes featured status.
20. Given a provider owns a verified finite Premium subscription, when they cancel with the current version, then cancellation is recorded for the paid expiry instant, entitlement remains active until that instant, and no refund/payment operation occurs; stale, expired, foreign, or no-expiry subscriptions are rejected without mutation.
21. Given an expiry job is replayed or a verified renewal covers the expiry boundary, when the job runs, then it emits at most one expiry event only for a real eligibility loss; a later verified renewal restores still-selected public listings and invalidates their cached featured state.

## Verification

Follow the [verification policy](../../../AGENTS.md#4-hard-limits-non-negotiable): manual acceptance evidence and existing non-test checks only; do not generate automated test files.

- Rules: exact ST-payment/ST-refund transitions, integer-paise caps, current plan lookup/cancellation state, event deduplication and immutable ledger insertion.
- Manual API/DB: provider fake success/failure/timeout, signed webhook verification, checkout event replay, cash collection, refund retries, subscription expiry boundary/renewal, delayed-job replay and ledger queries with keyset pagination.
- Authorization negatives: wrong role, non-owner vendor/provider, cross-business record identifier, inactive/unapproved business purchase, invalid internal event identity; assert 403/404 and no leaked records.
- Concurrency: duplicate webhook/refund event and simultaneous refund requests cannot exceed the remaining captured amount or create duplicate entries.
- Security: signatures checked before mutation; credentials/payment details excluded from logs and responses; plan/promotion keys allow-listed.
- Map AC1–AC21 to unit/contract/database scenarios; add provider timeout-after-capture, crash-before-order, both callback orders, stale purchase retry, signature/amount/currency mismatch, unsafe money integers, same-source/different-payload replay, cancellation-at-expiry and renewal exactly at/after the boundary. Assert financial conservation across shared charge budgets, no double ledger entry, at-most-once expiry notice, IST month boundaries and no raw financial evidence in telemetry.
