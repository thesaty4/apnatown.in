# BE: delivery

Features: F-RD-001, F-RD-002, F-RD-003, F-RD-004, F-RD-005, F-RD-006, F-RD-007, F-RD-008, F-AD-008, F-X-015 | Rules: BR-01, BR-02, BR-05, BR-06, BR-12, BR-14 | State machines: ST-delivery-job, ST-approval (rider) | Depends on: users, geo, settings, media-videos (private assets), payments (`recordCashCollection`); consumes Orders events; used by orders, admin, reviews.

Frontend counterpart: [FE delivery](../fe/delivery.md)

## Responsibility

Own rider application/approval, platform jobs/offers, secure customer handover codes for **all** modes, live tracking and immutable rider earning snapshots. Orders owns lifecycle/cases/stock; Payments owns collection/refund execution. Reviews owns rider ratings. Settlement authority/payout records remain decision-gated, not “marked paid by finance”.

Codes are 4-digit strings including leading zeros. Hash-only storage cannot serve repeatable reads: store a keyed verification hash **and encrypted retrievable ciphertext**, with keys outside the DB. Only the dedicated customer code channel decrypts. General order/job/history/SSE/admin/rider DTOs contain no plaintext. No payout rollup/table/settlement writer is specified until its policy/owner is approved.
`delivery_jobs` also stores `earned_distance_pay_paise bigint NULL CHECK >=0` and signed `earned_rounding_paise bigint NULL` with the earned snapshot. The displayed distance component uses shared integer-paise rounding; the final total rounds the exact base + distance expression once to the nearest rupee. Rounding adjustment = total − base − displayed distance component, so the immutable breakdown reconciles.
`delivery_codes` additionally persists `consumed_handover_id uuid NULL UNIQUE` and `consumed_by uuid NULL FK users`, paired with consumed_at; the receipt links Orders history and Payments collection without storing submitted plaintext.

## Rules and use-cases

1. **Ready/job creation:** consume `order.status_changed` to ready for configured `delivery + apna_town_rider` (final `js8.js` A.vready). Ensure one job per order; owner request/admin assignment/consumer replay converge on it. Earlier architecture wording “on accepted” must align to this prototype trigger. Pickup/self create **no** job; unconfigured provider/business fulfilment is unavailable, not default rider service.
2. **Offer/expiry:** configured selection policy chooses eligible approved/online/idle riders in the job city; nearest-idle is a recommendation, not an approved dispatch policy. One offered row/job, expiry `now+60s`. Insert each new offer and its `delivery.offer_created` outbox event in the same UoW, including a new offer after requeue; replay never emits a second logical creation or resets expiry. Reject/expiry revokes that offer and requeues; no candidates → requested job with assignment_state unassigned, notify admin. No indefinite live offer or guessed rider.
3. **Atomic acceptance/assignment:** lock the rider row **and** job/offer in consistent order; reassignment locks outgoing/incoming riders in ID order. Recheck live Users account/role, approval, online, city/dispatch eligibility, no active job, current order readiness, offer ownership/status/expiry and versions inside the transaction. Omitted expectedJobVersion is valid only when ensure creates a previously absent job; an existing job requires its current version. Partial unique active-rider index is the final backstop. Offline/suspension uses the same rider lock; suspension sets offline/revokes open offers without inventing post-custody recovery.
4. **Scope:** rider application scope is validated Geo city/area, not current GPS or a free-text area; incomplete drafts cannot enter scoped approval queues. Job scope is Orders' immutable pickup-business city/area. Review/documents, candidates, decisions, live GET/SSE and assignment check these discriminators; assigning admin must cover **both** job and rider. Same city/wrong area is denied; scope/permission changes revoke streams, not just next page load.
5. **Progress:** accepted → reached_shop → picked_up → reached_drop → delivered. Picking up requires current order ready and `checkedItemIds` equal all current fulfillable item IDs at the expected financial version; item count alone cannot implement the checklist. Changed/unavailable item resets checks. Fail from any active assigned step requires an enumerated reason; no delivered→fail. Before-pickup reassignment only; post-custody transfer/re-delivery stays gated Q-17.
6. **Codes:** CSPRNG issue at platform picked_up, self-dispatch, or pickup order ready. Persist HMAC bound to order/kind/generation plus authenticated-encrypted code and key versions; no plaintext at rest. Require configured expiry/cooldown and G-16 customer-channel approval before enabling the flow; do not assume SMS/provider choice. Repeat GET decrypts the **same** usable generation; it never creates/resets a code.
7. **Expiry/reissue/consume:** `now >= expiresAt`, consumed, invalidated, locked or wrong generation cannot verify/read as live. Customer reissue requires cooldown, expected generation and order eligibility; atomically invalidate old ciphertext/generation before new issuance. Carry failed-attempt count into the next generation; rate/attempt controls span generations so reissue cannot bypass lockout. Five wrong attempts lock/alert; recovery policy is gated, no vendor/rider reset bypass. Clear unusable ciphertext; retain only policy-approved metadata (retention Q-13).
8. **Verification transaction:** lock affected rider/order/job/offer/code/financial rows using the **same shared lock hierarchy** as assignment/cancellation; compare hash constant-time, then verify mode/readiness/current versions and explicit cash confirmation. Consume once with handover event/order transition/collection in one UoW; if any guard fails, do not consume. Use the foundation's typed rejected outcome to commit wrong-attempt/lock bookkeeping and its idempotent non-2xx result **before** mapping the error outside the transaction; retrying the same failed key does not count twice. Success replay returns the prior nonsecret result; new-key replay of a consumed code fails. Code reissue idempotency stores a generation reference and reauthorizes/re-decrypts only a still-live code, not cached plaintext. Store keyed request hashes for code-bearing commands, never plaintext in shared idempotency results.
9. **Cash:** platform complete, self-complete and pickup verify require explicit `cashCollected=true` only when current cash outstanding >0; use Payments' current version/verified handover, not a stored COD estimate/client amount. Prepaid/zero-due never creates a collection. For `settlementKind='no_charge'`, require durable `fundingSatisfied`, then perform normal code/fulfilment checks without cash confirmation. Financial status was internally settled by Payments, not by code match; show “No payment due”. Later payment-toggle changes cannot erase obligations.
10. **Failure/cancel:** publish exactly the outcomes below and invoke Orders' verified map in the shared UoW. Failure opens a real failed-delivery case/refund request as appropriate, never auto-approval. Only Orders releases recorded stock; after pickup no restock without goods-return policy. On order cancellation terminate open offers/job, free active rider slot and invalidate all codes; already failed/delivered jobs are not regressed.
11. **Minimization/tracking:** latest location only, no trail; active assigned rider sees delivery address, customer sees location only on picked_up/reached_drop leg. Recompute best-effort ETA from current permitted location/MapsPort, expose asOf/stale/unavailable rather than invented minutes. Calls require an active customer/assigned-rider relationship and configured masked-call provider; never fallback to raw phone.
12. **Earnings:** job creation stores an **estimate** with distance/base/per-km/settings/time. At verified completion calculate `round_to_nearest_rupee(basePaise + perKmPaise × distanceM / 1000)` using shared integer rounding, **current completion-time settings** and configured distance basis; persist earned distance/base/per-km/rounding/total/settings/time once. Never recalculate past earnings or call estimate “paid”. Missing earning/distance configuration blocks quoting that job, not a sample-value fallback.
13. **Periods/payout:** preserve final `js10.js` **rolling** filters: today/day `[asOf−24h,asOf)`, week `[asOf−7×24h,asOf)`, by earned/terminal timestamp with normalized half-open bounds. Return UTC period bounds/IST display; pin asOf in pagination so totals and rows agree. A switch to IST calendar day/week requires a decision, not a silent reinterpretation of the prototype labels. Failed/cancelled jobs have no earned amount. Settlement owner/period/evidence stays gated; no weekly row generation or mark-paid endpoint.
14. **Support:** job-linked dispute calls `OrdersCasePort.openForRider`, follow-up calls `addRiderNote`; recheck assignment/order link and never expose staff notes. No-job applicant/rider dispute delegates to Settings `SupportIntakePort.create({userId,message,source:'rider',sourceKey})` / existing `/support/messages`, respecting its validation/rate limits. Return actual persisted case/support ID, not a notification-only success.

## Events and jobs

Use [Orders' envelope/outcome map](../../orders/be/orders.md#event-contracts). Base fulfilment payload `{orderId,jobId?,scope,orderVersion,financialVersion,jobVersion?,actorUserId?,handoverId?,reasonKey?}` contains no code/address/raw phone.

| Producer → consumers | Exact event / effect |
|---|---|
| Delivery → Notifications/rider SSE | **`delivery.offer_created {offerId,jobId,riderUserId,expiresAt}`** with the commerce envelope (`aggregateId=offerId`, aggregateVersion=offer version; expiresAt is UTC). Emitted with offer insertion, not merely job creation. Recipient is riderUserId; dedupe by event/offer identity and never restart an expired/responded offer. No order-state transition, code, address or raw phone. |
| Delivery → Orders/Notifications | `delivery.job_created`, `delivery.assigned` (adds riderUserId), `delivery.unassigned`, `delivery.reached_shop`, `delivery.reached_drop`: projections only. |
| Delivery → Orders/Notifications | `delivery.picked_up` → out_for_delivery; `delivery.delivered` → delivered with `earningSnapshot`; `delivery.failed` → Orders' failure-only cancellation/case contract; `delivery.cancelled` acknowledges order cancellation, never creates a second refund. |
| Delivery → Orders/Notifications | `delivery.self_dispatched` → out_for_delivery, `delivery.self_delivered` → delivered, `delivery.pickup_completed` → picked_up. Each has no job ID and includes verified handover reference for completion. |
| Delivery → scoped support/Notifications | `delivery.code_locked {orderId,kind,codeVersion}`; no code/hash/ciphertext. |
| Delivery → Admin/Users/Auth/Notifications | `rider.application_submitted {riderUserId,applicationVersion,scope}`; `rider.application_decided {riderUserId,applicationVersion,scope,status,reasonKey?,decisionId}` after audited decision/Users grant. |
| Orders → Delivery | `order.status_changed` ready creates platform job or pickup code; `order.cancelled` cancels offers/job/codes; `order.items_adjusted` invalidates item/payable projection/checks by financial version. Final collection still rereads current amounts under lock. |

Jobs: `delivery.offer_expire`, code expiry cleanup and bounded outbox retry/reconciliation; compare current versions/status before work. No payout rollup or guessed settlement event. Same-UoW fulfilment apply and outbox replay share event ID, so no duplicate order/collection/code consumption.

## Acceptance criteria

1. Given platform/self/pickup orders, when accepted then ready events replay, then only the ready platform order gets one job; self/pickup get no job and an unconfigured provider gets no invented mode.
2. Given an offer expires at 60 s, when the rider taps Accept afterwards, then `DELIVERY_OFFER_EXPIRED` is returned and requeue follows the configured policy. Given an inserted/requeued offer and outbox retries, when published, then exactly one logical `delivery.offer_created` carries its four payload fields; rollback emits none and replay cannot restart the countdown.
3. Given two riders race for one job or one idle rider races to accept two jobs, when transactions commit, then exactly one active assignment survives. Concurrent offline/suspension/admin assignment rechecks the locked rider and cannot leave an unauthorized second job.
4. Given five distinct wrong-code attempts, when locked/reissued/retried, then brute-force state cannot reset; same-key replay does not add an attempt and admin alert is deduplicated.
5. Given platform, self or pickup cash handover, when code is valid but explicit collection is absent/current amount changed, then no consume, collection or final order transition occurs; with current versions/confirmation, all commit exactly once.
6. Given a rider is `pending` or `suspended`, when they try to go online, then `RIDER_NOT_APPROVED`.
7. Given a missing fail reason or a delivered job, when a rider submits fail, then validation/transition errors occur and no event is published.
8. Given same-city/wrong-area admin scope, when reading documents/live clusters/SSE, deciding or assigning an out-of-scope rider, then 403/no data or mutation; both job and rider scope are checked.
9. Given a vendor/rider/admin/other customer, when requesting the customer code, then 403/404; only the actual customer gets plaintext via the dedicated no-store channel, never an ordinary API/event/log.
10. Given a draft with only profile data, when saved/reloaded before vehicle/docs/payout, then it persists; submit rejects missing later requirements. An applicant can upload typed own KYC without a privileged rider role; only a successful durable ready result is attachable. Failed upload creates no pending attachment, and unregistered/foreign/wrong-purpose assets are rejected.
11. Given authorized approval, when its Users role grant or audit fails, then approval does not partially commit; forged profile role/status/online fields never grant permissions. Reload/session refresh sees only committed capability.
12. Given an active code, when its customer reloads repeatedly before expiry, then the same generation is recoverable from encrypted storage. At expiry/reissue/consume, old generation fails; concurrent verify/reissue has one winner and transaction rollback cannot consume a valid code.
13. Given item removal changes financial version, when a rider submits yesterday's checklist or COD amount, then pickup/completion conflicts and refetch exposes current labels/quantities/payable, not just item count.
14. Given self dispatch/completion or pickup verify, when an authorized owner submits valid versions/code/collection, then correct jobless event reaches Orders; wrong mode/nonowner/withdrawn approval cannot bypass it.
15. Given delivery failure before/after pickup, when replayed, then one case/cancellation/refund request is recorded, never approval/completion; only recorded pre-custody allocations can restore stock and post-custody goods remain held.
16. Given an order cancels as an offer is accepted or code verified, when transactions race, then one valid outcome wins; open codes/offers cannot resurrect cancelled orders and no cash is collected twice.
17. Given rate changes after estimate and again after completion, when completing then opening history, then estimate and completion-time earned snapshots remain distinct and history never recalculates; failed/cancelled jobs earn nothing.
18. Given jobs across IST midnight or rolling-24-hour/seven-day boundaries, when filtering/paginating, then counts and totals use pinned half-open periods once, not device timezone/calendar guesses; unavailable payout policy returns null/unavailable, not zero/paid.
19. Given a job-linked or jobless dispute, when duplicated, then exactly one actual Orders case or Settings support message is returned; foreign job/case notes and staff-only notes remain inaccessible.
20. Given location/call provider unavailable or permission revoked, when reconnecting/reading tracking/history, then stale/unavailable metadata replaces fabricated ETA; no raw phone, historical live address, location trail or cross-scope pin leaks.

## Verification

Follow the [verification policy](../../../AGENTS.md#4-hard-limits-non-negotiable): manual acceptance evidence and existing non-test checks only; do not generate automated test files.

- Map AC1–AC20 to domain/PostgreSQL/outbox checks with deterministic Clock/Maps/Media/Payments/Users/Reviews/Support fakes. Race checks use separate real DB transactions, including unique active-rider constraint, accept-vs-expiry/offline/suspension and cancellation-vs-cash/code.
- Security: encrypt/decrypt + HMAC/key rotation synthetic scenarios, exact-boundary expiry, failed-attempt persistence, reissue/verify/replay races, rollback and lost-response retry; inspect ordinary DTOs, idempotency records, SSE and logs for code/KYC/phone leakage.
- Input negatives: forged role/scope/price, NaN/out-of-range coordinates, oversized/pasted XSS notes/names, malformed/unregistered asset IDs, failed KYC upload, foreign job/code/case, rate limiting and stale private stream sessions. DTO money remains checked integer-paise JSON.
