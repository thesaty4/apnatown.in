Features: F-PF-001, F-PF-002, F-PF-003, F-PF-004, F-PF-005, F-PF-006, F-PF-007, F-PF-011, F-PF-012, F-PF-013, F-VD-001, F-VD-002, F-VD-003, F-VD-011, F-VD-018, F-PV-001, F-PV-002, F-PV-006, F-PV-007, F-X-011 | Rules: BR-01, BR-02, BR-06, BR-08, BR-12, BR-14, BR-16 | State machines: ST-approval | Depends on: users, geo, catalog | Used by: products, services, search, offers, cart-checkout, orders, reviews, engagement, media-videos, admin

Frontend counterpart: [FE businesses](../fe/businesses.md) · [Feature inventory](../../../docs/FEATURE_INVENTORY.md)

## Responsibility

Own shop/provider identity, public profile fields, location, weekly hours, delivery/pickup settings, onboarding applications and private business documents. Resolve owner and area from trusted context; never accept an owner ID or storage URL from a client. Users own account/role data; catalog owns categories; geo owns areas; products, services, orders, payments, reviews, engagement and media-videos own their respective records and actions.

Owner and `uploaded_by` are session-derived. Category and area IDs are explicit allow-listed fields validated against `catalog` and `geo`; client IDs never grant access. Media-videos validates/resolves asset IDs and alone owns file metadata/storage keys; KYC documents are never public. Profile edits do not create or alter records in the owning modules listed above.

For owner routes, `X-Business-Kind: shop|provider` selects which of the authenticated user's applications is intended; resolve ownership server-side. If exactly one exists the header may be omitted; if both exist, omission returns `BUSINESS_CONTEXT_REQUIRED`, never an arbitrary first business. The shared client derives it from vendor/provider route context; it grants no role, ownership or approval. Pending applicants may access profile/onboarding/limited overview by owned application capability without an approved seller role.
Businesses also owns the narrow `business.taxonomy-suggest` capability in [Catalog](../../catalog/be/catalog.md#rules-and-use-cases); resolve current ownership/editability/area in the registered policy, not from a client capability flag. This capability never authorizes Products, checkout or seller orders.

## DTOs and owner read contracts

- `BusinessProfilePatch`: `{expectedVersion,kind?,nameEn?,nameHi?,categoryIds?:uuid[],primaryCategoryId?,description?,areaId?,addressText?,location?:{lat,lng}|null,businessPhoneE164?,whatsappE164?,email?,instagramUrl?,youtubeUrl?,facebookUrl?,logoAssetId?,coverAssetId?,hours?:[{dayOfWeek,opensAt,closesAt,isClosed}],settings?:{temporarilyClosed?,deliveryMethod?,deliveryRadiusKm?,deliveryFeePaise?,minimumOrderPaise?,pickupEnabled?,pickupInstructions?,serviceRadiusKm?,serviceArea?,galleryMediaDefault?}}`. Category IDs are distinct active product categories and the primary ID must be in the set; a submitted profile has exactly one primary. Unknown/nested unknown fields fail validation. Profile/settings/hours/categories share the business version and one transaction; each supplied hours array replaces seven unique days. Kind is draft-only; provider service-area fields are rejected for a shop.
- Validate contacts and HTTPS social URLs without server-side fetching; clear optional values explicitly with null. Hours use IST wall time; missing draft fields are not silently filled. Holidays have no editor in the final source (`js9.js`); no holiday calendar or fake holiday data is added.
- An approved profile PATCH must preserve submission-required values despite nullable draft columns; it cannot clear identity/area and remain publicly approved. Public contacts are not login credentials.
- `BusinessPublicDto`: `{id,kind,slug,nameEn,nameHi,categories:[{id,slug,nameEn,nameHi}],primaryCategory,description,logo,cover,contacts,socialLinks,address,cityId,areaId,area,location?,weeklyHours,today,temporarilyClosed,delivery,pickup,serviceArea,serviceRadiusKm?,verified}`. `categories` contains product categories only; provider expertise remains Services-owned. `verified` is independent of approval. Resolved public assets never reveal raw keys. Personalized `distanceKm`/deliverability is a no-store read context, not a location-specific ISR cache entry.
- `BusinessReadPort.publicProjection({businessIds?,kind?,categoryIds?,context?,cursor?,limit?})` supplies that DTO to Search, Products/Services and public profiles, with current approved/non-deleted visibility. Unknown distance is null, never zero or a fabricated pin. `BusinessReadPort.forCheckout({businessIds})` returns `{businessId,status,cityId,areaId,location,hours,temporarilyClosed,deliveryMethod,deliveryRadiusKm,deliveryFeePaise,minimumOrderPaise,pickupEnabled,pickupInstructions,version}` only to checkout/delivery use-cases; server resolves destination eligibility.
- `BusinessReadPort.ownerSummary({businessId,actor})` validates ownership and composes `/businesses/me/overview`: `{business,status,capabilities,products?,orders?,earnings?,enquiries?,rating?,followers?,analytics?}`. Products supplies totals/low stock; `OrdersOwnerReadPort.summary` supplies order/open/waiting-for-rider counts, not revenue; `PaymentsOwnerReadPort.earningsSummary` supplies sales/earnings and explicit financial-policy availability. Pass identical UTC period bounds to both and display IST. Services supplies new/latest enquiries and real 7/30-day counts; Reviews/Engagement supply their own aggregates. Each section is `{state:"ready",data}` or `{state:"unavailable",code}`; unavailable money is null, never invented zero.
- Provider analytics composes Services' real enquiry counts/status mix and Q-11-approved view metrics. `views` and `conversionRate` stay explicitly unavailable until attribution/denominator are approved; do not hide available enquiry totals merely because view analytics is pending.
- `BusinessAdminReadPort.list/detail/summary` implements the exact [Admin read DTOs](../../admin/be/admin.md#required-owning-module-ports), including `view:'applications'|'listings'`, typed query/version/allowed actions and counts. Reauthorize trusted `AdminReadContext` before pagination or totals; private documents require approvals permission. This replaces separate `listForAdmin/detailForAdmin` aliases.
- `BusinessNotificationReadPort.context({businessId,eventVersion}) -> {ownerUserId,ownerRole,scope,nameEn,nameHi,status,reasonKey?}` is purpose-limited to Notifications. Return the committed decision version from the transaction's audit/outbox snapshot, not an unrelated later status; no phone, KYC or arbitrary profile fields.
- Public tabs bind concrete owners: `/businesses/public/{slug}/products` and `/businesses/public/{slug}/services` include counted pills; expertise uses Services. Offers, gallery/videos, reviews and follows use their linked module contracts. Reporting uses Admin's guest-capable listing-report intake, not a business-table mutation.
- Implement `BusinessMediaReadPort.context` with [Media's purpose-limited fields](../../media-videos/be/media-videos.md#required-discoverycommerce-read-ports), including raw logo/cover **asset IDs**, not recursively resolved media. It reads current approval, attachment and Gallery policy; unknown consent policy denies Gallery publication rather than guessing a grant.

The public projection also supplies owner-maintained read-only SQL expressions for [Search composition](../../search/be/search.md#rules-and-use-cases); Search applies predicates before pagination rather than filtering a first owner page in memory. Private scope/ownership/checkout reads are separate ports, never public SQL exports.

Open question: provider product ordering is required by F-PV-005, but the provider profile prototype has no product-delivery settings editor. Reuse the fulfilment contract, but do not invent a default fee/rider/pickup mode or a new visible editor before its configuration UX is approved. A business without configured delivery and without pickup has no available checkout mode; display that explicitly. Enabling delivery requires non-null method/radius/minimum and an explicit flat fee for self-delivery; null is not zero.

## Rules and use-cases

1. OTP verification/session creation is owned by `auth`. Create an application only for the authenticated user; `users` manages role assignment, and business ownership is always checked server-side.
2. `POST /businesses/applications` creates a business record; it does not create a user account or a QR record. Submission validates name, one or more active product categories with exactly one primary, area and address; it generates the unique immutable slug and enters `pending`. That is when the canonical QR target first exists. The QR payload is the existing `/shop/{slug}` or `/provider/{slug}` route, generated locally from the slug when the private owner QR screen renders; no QR asset/table, CDN request, analytics, or duplicate storage is introduced. Rename does not change slug; generic PATCH cannot alter it. Preserve ST-approval edges and capability limits: pending edits only, rejected/changes_requested can resubmit, suspended cannot sell or edit, inactive may reactivate. Never accept status in generic PATCH.
3. Admin decisions require `approvals` permission and assigned city/area scope (BR-12); check expected version, record actor/reason, audit before/after, and update status transactionally. Approval calls Users' internal role-assignment port for the matching vendor/provider role in that transaction; possession of that role never replaces a live business approval/capability check.
4. Public reads include only approved businesses. A non-public slug returns `BUSINESS_NOT_PUBLIC` without disclosing owner, application or document data. Cache invalidation follows status/profile changes.
5. Delivery eligibility reads `business_settings`; store fees/minimums in paise (BR-01) and let checkout calculate totals. Store coordinates only when provided; address entry does not require device geolocation.
6. Onboarding documents are optional; validate content and size through Media's asset port, store privately, and authorize every view (BR-14). Applicants can upload for their own draft before a vendor/provider role is granted; the trusted application context grants no selling/admin capability. Profile logo/cover use the same validated asset registry; only approved public responses resolve attached ready assets. Do not log document contents, raw keys or signed access URLs.
7. `verified_at` is not inferred from approval or an uploaded document; Q-41 must define awarding rules before the badge can be set.
8. `F-PF-007` reporting uses the admin-owned report flow. `F-PF-011/012`, QR/print and public profile actions call their owning modules or browser APIs; no cart, enquiry, follow, product, service, media, invoice or order data is duplicated here. F-X-011 invoice/order-slip data and layouts remain orders-owned.

## Events and jobs

- Publish `business.application.submitted`, `business.application.decision_changed` and `business.profile.changed` through the transactional outbox. Profile-change payloads include the before/after category IDs needed for cache invalidation.
- Decision events feed the notification contract; public profile/status changes trigger search/cache revalidation. Consumers are idempotent; retry transient failures through the shared outbox runner.
- Events carry `{businessId,ownerUserId,cityId,areaId,status,previousStatus?,version}`; the decision notification reads its stored reason through an internal recipient-scoped notice projection. There is no separate `business.status_changed` event.
- Category migration: backfill each non-null legacy `businesses.category_id` into `business_categories` as its primary; verify one-to-one parity before switching reads/writes. Deploy the join-table contract before dropping the legacy column in a later forward-only migration. Preserve service subcategory/expertise rows; do not infer additional business categories.
- The owner QR screen can render for the owner/applicant once a slug exists. Until the business is approved, scanning its canonical route returns `BUSINESS_NOT_PUBLIC`; suspended, inactive, soft-deleted or deleted profiles stay unavailable. QR generation is deterministic from the canonical URL, so retrying the local renderer creates no duplicate record. Slugs are immutable; no slug redirect/history contract is needed.
- No analytics event taxonomy, recurring business job or document-retention job is defined here; follow Q-11, Q-05 and Q-40.

## Acceptance criteria

- Given a verified applicant, when an application is created and submitted, then the authenticated user owns the draft and submit moves it to `pending` once; a repeated idempotency key returns the same result.
- Given a client sends another owner's ID, status, or storage URL, when it creates or patches a business, then the server ignores/rejects non-allow-listed fields and makes no unauthorized write.
- Given an area admin lacks `approvals:edit` or the business is outside assigned scope, when a decision is requested, then it is denied and status/audit data remain unchanged.
- Given a document is uploaded, when the request passes the approved content/size policy, then only private metadata is returned and a public profile response never contains the document or storage key.
- Given a business is not approved, when its public slug is read, then no owner/application data is returned and the response maps to the unavailable profile state.
- Given a concurrent update uses a stale version or invalid ST-approval edge, when the write is attempted, then it returns a stable conflict without partial changes.
- Given profile contact/social/hours/delivery fields and pickup instructions are edited, when saved/reloaded, then every supported field round-trips and the whole form uses one expected version.
- Given an applicant uploads a private document before approval, when another owner/public caller reads its asset ID, then access is denied and no role is self-granted.
- Given a scoped admin moves a listing to an unauthorized area, when the write checks both areas, then no profile/status/audit mutation is committed.
- Given one dashboard source fails, when overview loads, then that section reports unavailable/retry while other real owner-scoped summaries remain usable.
- Given one user owns a shop and a provider profile, when an owner API omits its business-kind context, then it returns an explicit context error rather than reading or editing the wrong business.
- Given a provider sells products but has no fulfilment configuration, when checkout asks for eligibility, then no fee or mode is invented and ordering is explicitly unavailable until configured.

## Tests

Unit: state transition guards, DTO allow-list, paise/settings validation, and public-field projection. Integration: PostGIS optional point, owner/document isolation, outbox commit/retry, and version conflicts. Authorization negatives: cross-owner access, missing `approvals:view/edit`, and out-of-area admin; never use real PII or document files.
